KCoral is a lightweight benchmark server that separates the agent loop from GPU execution. Agents write and revise code in their own workspaces; KCoral schedules remote evaluation and returns feedback for the next iteration.

Make GPU time count

Many agents. A shared GPU pool.

An agent needs a GPU for evaluation, while generation and compilation can run elsewhere. KCoral coordinates access so more agents can use the same hardware.

01 / SHARE

Share GPUs across agents

Keep multiple requests in flight. GPU stages take turns with exclusive access, while other requests can run CPU-only work. Agents use the returned checks and timings to guide their next revision.

Explore GPU scheduling ↗
02 / COMPILE

Free GPUs during compilation

Mark host-only functions with cpu_only=True to release GPU access while they run. Or compile on a separate CPU service, then send the library to a GPU service for evaluation.

Explore remote compilation ↗
03 / SCALE

One endpoint, multiple nodes

Distribute independent requests across GPUs and compute nodes. The Rust router selects healthy nodes with capacity; each node's supervisor manages and restarts its server.

Deploy a router ↗
04 / ISOLATE

Give each request its own space

With bubblewrap enabled, workers see read-only runtime dependencies and a private writable workspace. Requests return execution errors and logs so agents can fix a candidate and try again.

Configure filesystem isolation ↗
05 / REUSE

Reuse unchanged uploads

Content-addressed caches let clients skip sending the same tensors, files, and compiled libraries repeatedly. The Python client resends missing content automatically when a cache entry is unavailable.

Read about upload caching ↗
06 / CONNECT

Develop for remote hardware

Run your agent on a laptop or CPU host and evaluate kernels on the target GPU, including edge devices such as NVIDIA Jetson Thor. Connect your own harness through the client, CLI, or protocol.

The KCoral protocol

Four operations. Your evaluation workload.

A program is a sequence of operations sent over HTTP. Upload your own code and data, call functions, and choose the results to return, alongside execution status and logs.

  1. upload

    Send source code, tensors, bytes, libraries, or files.

  2. get_function

    Select a named function or object from a module or library.

  3. run

    Call a function with arguments and keep its returned value.

  4. return

    Select values, files, or folders for the response.

Read the protocol ↗

For a simple Python call, use @client.function() and .remote(). KCoral builds and submits the program for you.

KCoral CLI

Familiar tools.
Remote execution.

Run Python, Compute Sanitizer, Nsight Compute, run-iket, or shell commands on a worker. Upload an experiment directory and bring back diagnostics and profiler reports.

Set KCORAL_URL to your server or router. Options before -- control KCoral; arguments after it go to the remote tool.

Explore the CLI tools ↗
Check, debug, and profile
# Connect to your team's GPU service
export KCORAL_URL='http://gpu.example.com:8000'

# Run your correctness check
kcoral run python --send experiment -- experiment/check.py

# Find CUDA memory errors
kcoral run compute-sanitizer --send experiment \
  -- python experiment/check.py

# Download an Nsight Compute report
kcoral run ncu --send experiment --out artifacts/ncu \
  -- --set basic -- python experiment/capture.py

Evaluation

Measured on a single NVIDIA B200.

We evaluated timing fidelity, shared-GPU throughput, and recovery after candidate failures. These results describe the workloads and settings below.

0.425%

Median timing difference

Across 500 workloads from 82 TIRx-kernels families. The 95th percentile difference was 3.136%; 497 of 500 workloads were within 5% of local timing.

2.58×

Evaluation throughput

12.86 workloads/min versus 4.98 locally, over 256 cold-cache evaluations with 32 requests in flight and 32 workers sharing one GPU.

200/200

Successful follow-up requests

All 200 candidate cases matched their expected outcomes. A known-good GPU request succeeded after every case on the same server instance.

Workloads and measurement scope

Timing fidelity uses the same GPU, inputs, and timing settings, including L2 flushing. The reported difference is 100 × |remote − local| / local. Timings cover kernel execution and exclude compilation, input preparation, and request latency. The three differences above 5% occurred on 1.9–2.2 μs normalization kernels, with absolute differences of 0.13–0.38 μs.

Throughput uses eight fixed TIRx-kernels specializations repeated 32 times each. Each evaluation compiles from a cold cache, prepares GPU inputs, and benchmarks an existing kernel. CPU preparation and compilation are marked cpu_only=True. Requests take turns accessing the GPU; the local baseline runs sequentially. Agent generation time is excluded.

The robustness suite contains CUDA, Triton, and CuTeDSL candidates with compilation or architecture rejections, numerical mismatches, runtime errors, and worker exits. After each case, a fresh request runs known-good GPU sum and matrix multiplication operations. This measures recovery from the tested failures.
